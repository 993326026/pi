持久化 AgentHarness / 会话设计说明。

## 框架

完全持久化的 `AgentHarness` 本身是不现实的，因为重要的依赖项是由宿主应用程序提供的运行时 JavaScript：

- 工具实现
- 模型/认证提供者
- 扩展和钩子处理程序
- 资源加载器
- 系统提示回调/修饰符

实际目标是一个半持久化的 harness：

- 会话是持久化的仅追加状态树
- harness 将其拥有的状态持久化到会话条目中
- 宿主应用程序负责在恢复时重新创建兼容的非持久化依赖项
- 恢复从持久化边界重新启动，而不是从正在进行的提供者流重新启动

## 会话拥有持久化状态

将会话视为所有持久化的 agent 状态，而不仅仅是对话历史。

现有的会话状态已经包含了 harness 状态：

- 模型变更
- 思考级别变更
- 叶子条目
- 标签
- 压缩和分支摘要
- 自定义消息和自定义条目

这表明继续使用一个持久化的会话日志，而不是添加 harness 附带存储。附带存储对于大 blob 可能仍然有用，但会话条目应保持事实参考源。

## 应用程序在恢复时必须提供什么

应用程序必须重新创建兼容的运行时依赖项：

- 模型注册表 / 模型对象
- 工具注册表
- 扩展集、版本和顺序
- 资源加载器
- 系统提示提供者/钩子
- 认证提供者
- 应用程序特定的钩子

Harness 可以在可用时验证稳定的 ID/版本/哈希，但它不能自己序列化这些依赖项。

## Harness 应该持久化什么

最小有用的持久化条目：

- 排队的引导/跟进/下一轮消息
- 与回合关联的队列消耗
- 在活动操作期间接受的待处理会话写入
- 待处理写入应用状态
- 操作开始/完成/中断
- 回合开始/完成
- 提供者请求开始/完成（如果需要用于恢复诊断）
- 工具调用开始/完成（如果我们想要安全的工具恢复）

潜在条目：

```ts
type DurableHarnessEntry =
  | QueueEnqueuedEntry
  | QueueConsumedEntry
  | PendingWriteEnqueuedEntry
  | PendingWriteAppliedEntry
  | OperationStartedEntry
  | OperationFinishedEntry
  | OperationInterruptedEntry
  | TurnStartedEntry
  | TurnFinishedEntry
  | ProviderRequestStartedEntry
  | ProviderRequestFinishedEntry
  | ToolCallStartedEntry
  | ToolCallFinishedEntry;
```

每个接受的变更必须在公共 API 解析之前是持久化的。

## 恢复模型

启动时：

1. 宿主应用程序注册工具/模型/扩展/资源/认证/钩子。
2. Harness 打开会话。
3. Harness 将会话条目归约为：
   - 当前叶子
   - 对话分支
   - harness 配置
   - 队列
   - 待处理写入
   - 活动操作/回合/工具状态
4. Harness 验证所需的运行时依赖项。
5. Harness 协调未完成的操作状态。

提供者流不可恢复。恢复只能从持久化边界重试或标记操作已中断。

## 恢复策略

默认保守策略：

- 未完成的 agent 回合：标记为中断，保留持久化的队列/待处理写入，返回空闲
- 未完成的提供者请求：标记为中断；不自动重试
- 未完成的工具调用：附加中断/错误工具结果；仅在工具声明重试安全/幂等时重试
- 未完成的压缩：如果不存在压缩条目，则重新运行
- 未完成的分支摘要/树导航：如果安全，则重新运行/应用缺失的摘要或叶子条目

可选策略：

```ts
recovery: "mark_interrupted" | "retry_unfinished"
```

`retry_unfinished` 必须围绕非幂等工具调用进行防护。

## 关键场景

### 队列

- 在 `queue_enqueued` 之前崩溃：消息未被接受。
- 在 `queue_enqueued` 之后崩溃：消息被恢复。
- 在队列排空之后但在持久化回合记录之前崩溃：存在丢失/重复的风险。
- 必需的不变量：消耗的队列 ID 必须在被视为已消耗之前记录在 `turn_started` 或等效项中。

### 待处理写入

- 在 `pending_write_enqueued` 之前崩溃：写入未被接受。
- 在排队之后但在应用之前崩溃：恢复应用它。
- 在应用之后但在应用标记之前崩溃：确定性的目标条目 ID 允许恢复检测条目已存在并标记为已应用。

### Agent 循环回合

- 在提供者请求之前崩溃：重试或标记为中断。
- 在提供者请求期间崩溃：默认标记为中断。
- 在提供者响应之后但在助手消息持久化之前崩溃：除非提供者结果被记录，否则响应会丢失。
- 在助手消息持久化之后崩溃：从持久化消息恢复。

### 工具调用

- 在工具调用开始之后但在结果之前崩溃：外部副作用可能已经发生。
- 默认恢复不应重新运行非幂等工具。
- 工具调用需要稳定的 ID 和重试安全元数据以进行自动恢复。

### 压缩

- 在摘要生成之前崩溃：重新运行准备/摘要。
- 在生成的摘要之后但在压缩条目之前崩溃：除非摘要被记录，否则重新运行。
- 在压缩条目之后崩溃：操作完成；如果缺失则附加完成标记。

### 分支摘要 / 树导航

- 在摘要之前崩溃：重新运行或标记为中断。
- 在摘要条目之后但在叶子条目之前崩溃：附加缺失的叶子条目。
- 在叶子条目之后崩溃：操作完成；如果缺失则附加完成标记。

## 最小可行原型

1. 添加持久化队列条目。
2. 添加具有确定性目标 ID 的持久化待处理写入条目。
3. 添加操作开始/完成/中断条目。
4. 添加带有已消耗队列 ID 的回合开始。
5. 通过归约会话日志来恢复。
6. 默认将未完成的 agent 回合标记为中断。
7. 仅在不存在最终条目时重新运行未完成的压缩/树操作。
8. 除非工具元数据表示重试安全，否则不重试未完成的工具调用。

## 开放问题

- 哪些 harness 配置条目应该首先移动到会话中：工具、活动工具、资源、流选项、系统提示引用？
- 已解析的系统提示文本是否应该每个回合快照一次用于审计/调试？
- 我们在恢复时是否需要严格的依赖项 ID/版本匹配？
- 应该记录多少提供者请求数据？
- 恢复应该附加用户可见的助手中断消息还是仅内部操作条目？
- 存储在恢复期间是否应该支持截断最终的部分 JSONL 行？
